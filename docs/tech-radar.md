# Tech Radar — кандидаты на будущий переход

Копилка технологий, на которые хотим перейти в будущем, чтобы не потерять идею между релизами.
Это **не** обязательство и не план на ближайший спринт — это backlog апгрейдов: что, зачем, и
по какому триггеру переходить. Пополняется по ходу обсуждений.

## Политика

- **Пре-релизные / ещё не зарелиженные технологии — допустимы**, если выгода ясна, а риск
  приемлем. Прецедент уже в проде разработки: backend использует **`ty`** (пре-релизный
  тайпчекер Astral, ещё не зарелижен) вместо mypy.
- Предпочтение — **тулинг-ускорителям** (быстрее линт/сборка/тайпчек) перед сменой парадигмы
  (фреймворк/архитектура): низкий риск, высокая отдача, легко откатить.
- Кандидат на смену *фреймворка/архитектуры* заводится сюда только с явной продуктовой выгодой,
  а не «потому что моднее».

## Кандидаты — frontend tooling

### oxc formatter — перейти на oxlint и для форматирования
- **Контекст:** линтер уже мигрирован с ESLint на **oxlint** (CHANGELOG 2026-06-11) — ESLint и
  его плагины удалены, oxlint единственный линтер (`react`-плагин включён, правила
  `rules-of-hooks` / `exhaustive-deps` / `only-export-components` сохранены). Type-aware не
  внедряли: проект использует `tseslint.configs.recommended` (non-type-checked), таких правил в
  конфиге не было. Осталось закрыть **форматирование**.
- **Что:** форматтер от `oxc` (та же тулчейн-семья, что и `oxlint`).
- **Зачем:** в проекте сейчас **нет форматтера** (стиль держал только линтер). Форматтер `oxc`
  даст линт + формат одной тулчейн-семьёй, без второго инструмента (`Biome` не нужен).
- **Заменяет/дополняет:** закрывает отсутствующий форматтер; ничего существующего не заменяет.
- **Статус (июнь 2026):** форматтер `oxc` — в разработке, ещё не выпущен.
- **Триггер:** когда `oxc` выпустит форматтер стабильно — подключить `format`-скрипт + цель
  `make format` (зеркалит backend `make format` на ruff).
- **Риск:** низкий — добавление форматтера на пустое место, ломать нечего.
- **Заметка (на будущее):** если позже понадобятся type-aware правила (`no-floating-promises`
  и пр.) — включать через oxlint type-aware (alpha с 8 дек 2025, 43/59 правил `typescript-eslint`,
  поверх `tsgolint`/TS 7); сейчас проект их не использует.

### Rolldown-vite
- **Что:** Vite на **Rolldown** — Rust-бандлере (замена Rollup), который делает сама команда Vite.
- **Зачем:** ускорение `vite build` «даром», прозрачно под капотом.
- **Заменяет/дополняет:** Rollup-бандлер внутри текущего Vite 8 (drop-in).
- **Статус:** в активной разработке, движется к тому, чтобы стать дефолтом Vite.
- **Триггер:** когда стабилизируется / станет дефолтным бандлером Vite.
- **Риск:** низкий — прозрачная замена внутреннего бандлера, API Vite не меняется.

### TanStack DB — реактивные коллекции поверх Query
- **Что:** слой коллекций НАД TanStack Query: live-запросы к клиентскому стору, оптимистичные
  транзакции, join'ы между коллекциями.
- **Зачем:** когда один экран начнёт склеивать несколько источников (поездки + профиль +
  статистика) и захочется оптимистичных правок без ручной сборки данных в компоненте.
- **Заменяет/дополняет:** надстраивается над уже внедрённым TanStack Query (CHANGELOG 2026-08-22),
  инкрементально — переезжать целиком не требуется.
- **Триггер:** появление экрана с cross-collection чтением или оптимистичным редактированием
  (кандидаты — редактирование поездки, дашборд статистики).
- **Риск:** средний — свой слой состояния поверх кэша; заводить под конкретный экран, не «на вырост».

### ~~tsgo (TypeScript 7, нативный компилятор)~~ — ВНЕДРЁН
- **Что:** нативный компилятор TypeScript на **Go** (Microsoft), ~10× быстрее прежнего `tsc`.
- **Статус:** запинен в `frontend/package.json` как `typescript: ~7.0.2` (приехал автобампом
  Dependabot, поэтому карточка какое-то время оставалась в кандидатах по недосмотру).
  `npm run typecheck` = `tsc -b` уже идёт на нём.
- **Итог внедрения (проверено 2026-07-18):** переход с 6.0.3 на 7.0.2 не дал ни одной ошибки
  типов. Заодно на этой же базе включён `strict: true` в обоих tsconfig — тоже ноль ошибок,
  код был написан strict-совместимо, флаг просто не стоял.

## Кандидаты — backend tooling

### Granian — Rust ASGI-сервер
- **Что:** один Rust-бинарь (ASGI + собственный RSGI) вместо `uvicorn` (+`gunicorn` как process-manager).
- **Зачем:** выше RPS, проще деплой (gunicorn не нужен — Granian сам держит multi-process/thread),
  стабильнее хвост латентности; RSGI снижает per-request overhead (lightweight-объект вместо большого dict).
- **Заменяет/дополняет:** `uvicorn` (текущий ASGI-сервер в deps).
- **Статус (июнь 2026):** прод-готов, но младше uvicorn.
- **Триггер:** только когда сервер станет **измеренным** боттлнеком, либо нужен one-binary-деплой /
  RSGI. На DB-bound CRUD-API выигрыш ~10% (каждый запрос блокируется на БД); основной выигрыш —
  в connection-heavy сценариях. Поэтому по триггеру, не прямо сейчас.
- **Риск:** средний — смена рантайма сервера, ставка на более молодой проект.

### pyx — приватный реестр пакетов Astral (watch-only)
- **Что:** новый от Astral — быстрый/безопасный комплемент к PyPI: приватные пакеты + ускоренные
  публичные установки.
- **Зачем:** в `ruff`-конфиге исключён `service-lib` «for local development» — если это общая
  внутренняя либа, pyx мог бы её хостить и ускорить CI-установки.
- **Заменяет/дополняет:** дополняет PyPI/uv-резолв; ничего существующего не заменяет.
- **Статус (июнь 2026):** новое, экосистема Astral (та же семья, что `ruff`/`uv`/`ty`). **Watch-only.**
- **Триггер:** когда появится реальная нужда в приватном пакете (вынос `service-lib`) и pyx
  стабилизируется.
- **Риск:** н/д (наблюдение, не внедрение).
