# Архитектура проекта

Бэкенд (`backend/app/`) построен по **Domain-Driven Design**: нарезка по доменам (`auth`, `users`), а не по слоям — весь код одной сущности собран в одном месте. Фронтенд (`frontend/`) — отдельный Vite/React SPA; весь стек поднимается из корня одной командой (`make run`; compose-файлы и инфра-конфиги живут в `ops/`).

> **Детальная структура и конвенции — в `.claude/rules/` и `.claude/skills/`**; что где лежит, перечислено в разделе «Карта» файла [`CLAUDE.md`](../CLAUDE.md). Это единый источник истины.
>
> **Дерево файлов здесь намеренно не дублируется.** Оно выводится из кода (`find backend/app`, `grep`) и в ручной доке быстро устаревает — поэтому актуальную структуру всегда смотри в самом коде, а не в этом файле. Этот документ держит только то, что из кода *не* выводится: принципы и причины.

## Слои домена

Каждый домен самодостаточен и делится на четыре слоя:

1. **domain/** — чистая бизнес-логика: entities, value objects. Без инфраструктурных импортов.
2. **infra/** — SQLAlchemy-модели БД, репозитории, UnitOfWork, внешние клиенты.
3. **application/** — use cases (`*Service`), входы `*Command`, результаты `*Result`.
4. **presentation/** — HTTP-схемы (`*Request` / `*Response`), роуты, dependencies.

Presentation-схемы отделены от application-DTO, чтобы не протекали абстракции; конверсия живёт в route, без отдельного слоя мапперов: входящая команда собирается явно по полям (новое поле транспорта пропускается внутрь осознанно), ответ — одной строкой `model_validate(..., from_attributes=True)`.

**Учётная запись и профиль — разные домены.** `auth` владеет тем, по чему пользователь входит: email, username, пароль, подтверждение email (`GET /v1/auth/me/`). Оба идентификатора сравниваются без учёта регистра, уникальность держат индексы по `lower()`; email хранится в нижнем регистре, username — как ввели. `users` хранит только профиль — отображаемое имя и согласия (`GET /v1/users/me/`); при регистрации `auth` передаёт ему `display_name`, равный username, и больше ничего о логине. Валидный токен без учётной записи — это 401 `auth.account_not_found`: токен никого не идентифицирует.

## Почему так

- **Высокая связность / низкая связанность** — домены изолированы, код сущности собран вместе.
- **Масштабирование** — домен можно вынести в отдельный микросервис без переписывания.
- **Гибкость транспорта** — можно добавить GraphQL/gRPC-presentation поверх тех же application-сервисов.

## Общая инфраструктура

`backend/app/shared/` нарезана **по вертикалям-интеграциям** (postgres, procrastinate, email, http, jwt, crypto, di, logging) — каждая интеграция самодостаточный пакет с lifecycle-компонентом, клиентами и протоколами. Состав вертикали — её `__init__.py`; критерий «Component+Registry vs `@cache`-factory» — в `.claude/rules/python/component-lifecycle.md`, правила работы с `shared/` — в `.claude/rules/python/shared-infrastructure.md`.

## Локализация топонимов: страны и города

Сквозной принцип (тот же, что у кодов ошибок `messageForCode`): **бэк хранит и отдаёт стабильный идентификатор, отображаемое имя резолвит фронт по активной локали.** Имена на конкретных языках в БД не хранятся.

- **Страны — ISO 3166-1 `alpha-2`** (`BY`, `RU`): единый формат в БД, API, фронте и `frontend/data/world-countries.geo.json` (источник; карта читает собранный из него TopoJSON). Имя резолвится на клиенте через `Intl.DisplayNames` (CLDR встроен в браузер), раскраска карты — матчинг по коду. Код страны клиент не присылает: бэк берёт его из газеттира вместе с городом. Почему alpha-2, а не alpha-3: `Intl.DisplayNames`, флаги-эмодзи и geojson работают с alpha-2; alpha-3 потребовал бы клиентский маппер. Новый язык не трогает БД.
- **Города — наш `cityId` из справочника `geo`.** Стандартного кода у городов нет, `Intl` их не переводит, поэтому перевод — ответственность **данных**: газеттир `geo_cities` хранит названия колонкой на язык (`name_en` обязательно, остальные — если перевод есть). Поездка хранит только `cityId` + страну + координаты; названия фронт запрашивает у geo (`POST /v1/geo/cities/resolve/`) на языке интерфейса, при отсутствии перевода получает английское. `cityId` = uuid5 от ключа поставщика (`"GeoNames:524901"`) — стабилен на любом окружении и при перезагрузке справочника, поэтому его можно хранить. Город и место (природный объект, достопримечательность) — разные сущности: у города ровно одна страна, у места их может быть несколько (`.claude/decisions/geo.md`).
- **Газеттир — воспроизводимые датасеты.** Файлы в нашем формате (`backend/app/geo/infra/datasets/FORMAT.md`) лежат ассетами GitHub Release (теги `geo-data-v*`), в git — манифест (версия, url, sha256, формат) и загрузчик. Формат датасета задаёт таблицу: города (GeoNames) — `geo_cities`, места (Wikidata) — `geo_places`. Загрузка — upsert по id, объекты не удаляются: их id хранят те, кто на них ссылается. Журнал загруженных версий — `geo_dataset_loads`.
- **journeys → geo — один узкий вызов**: клиент присылает только `cityId` городов, а journeys при создании и правке поездки и при расчёте расстояния берёт у geo их страну и координаты (`CitiesClientPort` → `InternalCitiesClient`, по образцу `InternalUsersClient`), до открытия транзакции. Ответ сопоставляется по `cityId`, не по порядку; города нет — `journeys.unknown_city`. geo о своих потребителях не знает.

Симметрия: и страна, и город приходят как `{ id, … }`; фронт резолвит имя по `id + locale`. У стран провайдер — платформенный (`Intl`), у городов — данные с бэка. Не «клиент vs бэк», а «идентификатор → имя там, где есть источник перевода».
