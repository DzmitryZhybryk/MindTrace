# Архитектура проекта

Бэкенд (`backend/app/`) построен по **Domain-Driven Design**: нарезка по доменам (`auth`, `users`), а не по слоям — весь код одной сущности собран в одном месте. Фронтенд (`frontend/`) — отдельный Vite/React SPA; весь стек поднимается из корня одной командой (`make run`; compose-файлы и инфра-конфиги живут в `ops/`).

> **Детальная структура и конвенции — в [`CLAUDE.md`](../CLAUDE.md)** (секции «Architecture», «Shared infrastructure», «DTO conventions», «Service Result / Command convention», «Cводная таблица именования по слоям», «Versioning & changelog»). Это единый источник истины.
>
> **Дерево файлов здесь намеренно не дублируется.** Оно выводится из кода (`find backend/app`, `grep`) и в ручной доке быстро устаревает — поэтому актуальную структуру всегда смотри в самом коде, а не в этом файле. Этот документ держит только то, что из кода *не* выводится: принципы и причины.

## Слои домена

Каждый домен самодостаточен и делится на четыре слоя:

1. **domain/** — чистая бизнес-логика: entities, value objects. Без инфраструктурных импортов.
2. **infra/** — SQLAlchemy-модели БД, репозитории, UnitOfWork, внешние клиенты.
3. **application/** — use cases (`*Service`), входы `*Command`, результаты `*Result`.
4. **presentation/** — HTTP-схемы (`*Request` / `*Response`), роуты, dependencies.

Presentation-схемы отделены от application-DTO, чтобы не протекали абстракции; конверсия — одной строкой в route (`model_validate(..., from_attributes=True)`), без отдельного слоя мапперов.

## Почему так

- **Высокая связность / низкая связанность** — домены изолированы, код сущности собран вместе.
- **Масштабирование** — домен можно вынести в отдельный микросервис без переписывания.
- **Гибкость транспорта** — можно добавить GraphQL/gRPC-presentation поверх тех же application-сервисов.

## Общая инфраструктура

`backend/app/shared/` нарезана **по вертикалям-интеграциям** (postgres, procrastinate, email, http, jwt, crypto, di, logging) — каждая интеграция самодостаточный пакет с lifecycle-компонентом, клиентами и протоколами. Критерий «Component+Registry vs `@cache`-factory» и разбор каждой вертикали — в `CLAUDE.md` → «Shared infrastructure».

## Локализация топонимов: страны и города

Сквозной принцип (тот же, что у кодов ошибок `messageForCode`): **бэк хранит и отдаёт стабильный идентификатор, отображаемое имя резолвит фронт по активной локали.** Имена на конкретных языках в БД не хранятся.

- **Страны — ISO 3166-1 `alpha-2`** (`BY`, `RU`): единый формат в БД, API, фронте и `frontend/src/data/world-countries.geo.json`. Имя резолвится на клиенте через `Intl.DisplayNames` (CLDR встроен в браузер), раскраска карты — матчинг по коду. Бэк валидирует код на границе (`pycountry`). Почему alpha-2, а не alpha-3: `Intl.DisplayNames`, флаги-эмодзи и geojson работают с alpha-2; alpha-3 потребовал бы клиентский маппер. Новый язык не трогает БД.
- **Города (и любые места) — наш `placeId` из справочника `geo`.** Стандартного кода у городов нет, `Intl` их не переводит, поэтому перевод — ответственность **данных**: газеттир `geo_places` хранит названия колонкой на язык (`name_en` обязательно, остальные — если перевод есть). Поездка хранит только `placeId` + страну + координаты; названия фронт запрашивает у geo (`POST /v1/geo/places/resolve`) на языке интерфейса, при отсутствии перевода получает английское. `placeId` = uuid5 от ключа поставщика (`"GeoNames:524901"`) — стабилен на любом окружении и при перезагрузке справочника, поэтому его можно хранить.
- **Справочник мест — воспроизводимый датасет.** Файл в нашем формате (`backend/app/geo/infra/datasets/FORMAT.md`) лежит ассетом GitHub Release (теги `geo-data-v*`), в git — манифест (версия, url, sha256) и загрузчик. Загрузка — upsert по `placeId`, места не удаляются: на них ссылаются поездки. Журнал загруженных версий — `geo_dataset_loads`.
- **journeys → geo — один узкий вызов**: при создании поездки journeys спрашивает у geo, каких мест нет (`PlacesClientPort` → `InternalPlacesClient`, по образцу `InternalUsersClient`), до открытия транзакции. geo о своих потребителях не знает.

Симметрия: и страна, и город приходят как `{ id, … }`; фронт резолвит имя по `id + locale`. У стран провайдер — платформенный (`Intl`), у городов — данные с бэка. Не «клиент vs бэк», а «идентификатор → имя там, где есть источник перевода».
