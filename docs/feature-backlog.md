# Бэклог отложенных фич

Файл-память: фичи, по которым решение «делаем, но позже» принято осознанно — чтобы не
потерять. Пункт заводится при откладывании, удаляется при отгрузке фичи. Не путать с
`.claude/.current-plan.md` — тот живёт только на время активной задачи и gitignored.

## 1. Удаление и редактирование аккаунта (users)

Скоро в работу (решение 2026-08-18). Сейчас у `users.deleted_at` нет писателя (только ручной
SQL), а `display_name` пишется только при регистрации (= username, update-эндпоинта нет):
контракт 410 `users.user_deleted` и фронтовый разлогин по нему уже готовы и ждут фичу.

- **Редактирование профиля**: PATCH-эндпоинт (минимум `display_name`). `display_name` —
  NOT NULL без фоллбэка на фронте, поэтому на записи trim и отказ на пустую строку
  (иначе «Hello, » с висящей запятой); write-path закрывает отложенную PLAUSIBLE-находку
  ревью про непустоту display_name.
- **Удаление аккаунта**: кнопка на фронте + эндпоинт, пишущий `deleted_at` (soft-delete).
  Открытые продуктовые вопросы, решить при дизайне: должен ли удалённый логиниться/рефрешить
  токены (сейчас — да: login ищет по `user_credentials` без предиката `deleted_at` → петля
  «login → 410 на /me → разлогин»); grace-период восстановления; судьба journeys и
  `user_credentials`/refresh-токенов (отзывать ли активные сессии при удалении).
- **`deleted_at` в auth нигде не читается**: ни login/refresh, ни `GET /v1/auth/me/`, ни
  подтверждение email (`user_credentials_entity.is_deleted` не проверяется). Закрывать всё
  разом, не по одному эндпоинту: soft-delete не удаляет refresh-токены (каскад только на
  физический DELETE), поэтому 401 `auth.account_not_found` из одного `/v1/auth/me/` даст
  «401 → refresh проходит → снова 401» без разлогина. FK между `users` и `user_credentials`
  нет — фича решает, какой из двух `deleted_at` главный, или пишет оба.
- Конвенция чтения soft-deleted зафиксирована в `.claude/rules/python/ddd.md`
  (point-lookup отдаёт всё + entity-guard; списки фильтруют в SQL по умолчанию).
